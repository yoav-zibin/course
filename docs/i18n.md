# Languages (i18n) for frontends

The backend serves the platform's texts in several languages, so every frontend (web,
Android, iOS, React Native) can show the same translations without carrying its own.
Frontends choose how to use them in their UI.

Supported languages: `en` English, `es` Español, `fr` Français, `de` Deutsch,
`pt` Português, `zh` 中文（简体）, `hi` हिन्दी, `ar` العربية (right to left).
`GET /i18n/locales` is the authoritative list.

## 1. Pick a language

For every request, the backend answers in the first of these that is set:

1. `?lang=es` on the request (explicit choice).
2. The language saved on the user named by the `X-User-Id` header
   (`PATCH /users/{id}` with `{"locale": "es"}`; `POST /users` accepts `locale` too).
3. The `Accept-Language` header (browsers and mobile HTTP clients send it already).
4. English.

Tags like `es-MX`, `pt_BR` or `zh-Hant-TW` are accepted and mapped to their language
(every Chinese variant gets Simplified Chinese). A `locale` of `""` clears the saved
language. Responses carry `Content-Language` with the language used.

## 2. Get the texts

```
GET /i18n/locales                 languages: code, own name, English name, direction
GET /i18n/es                      every text in Spanish
GET /i18n/es?prefix=ui.           only keys starting with "ui."
GET /i18n/es?fallback=false       only what Spanish itself defines (default fills gaps from English)
```

```json
{
  "locale": "es",
  "direction": "ltr",
  "version": "9f2c4e1ab07d",
  "messages": {"ui.action.save": "Guardar", "ui.match.moves_count": "Movimientos: {count}", "...": "..."}
}
```

- Fill `{placeholders}` in the client: `text.replace("{count}", n)`.
- There are no plural forms. Write UI so the count stands alone (`Moves: {count}`).
- `direction` is `"rtl"` for Arabic: set `<html dir="rtl">` / mirror the layout.
- The response has an `ETag` (also `version`) and `Cache-Control: no-cache`: keep a copy,
  and send `If-None-Match` to get a cheap `304` while nothing changed (browsers do this
  by themselves). Don't cache it for longer: a new translation should show after a deploy.

Key groups:

| Prefix | Texts |
|--------|-------|
| `ui.*` | Common portal and builder labels (nav, sign in, actions, sections, game modes, builder fields) |
| `status.*`, `end_reason.*`, `seat.*` | Labels for the API's values: `status.waiting_for_players`, `end_reason.player_left`, `seat.computer` |
| `error.*` | The platform's error messages (see below) |

For example, show a match's status with `messages["status." + match.status]`.

## 3. Errors

Error responses keep `detail` and add `code` (and `params` when the message mentions
values):

```json
{"detail": "partida no encontrada", "code": "match_not_found"}
{"detail": "se esperaban 7 movimientos pero la partida tiene 0", "code": "expected_moves",
 "params": {"expected": "7", "actual": "0"}}
```

- `detail` is in the request's language and is safe to show.
- `code` is the same in every language: branch on it, not on the text. It is the key
  without `error.`, so `messages["error." + code]` is the template if you want to render
  the message yourself from `params`.
- `code` is `"unknown"` for a message that has no catalog entry (the English text is
  returned). Validation errors (422) are not translated.

## 4. Adding a language or a text (backend)

- **A text:** add the key to `locales/en.json`, then to every other `locales/*.json`. The
  tests fail when a file lacks a key or has different `{placeholders}`.
- **An error message:** the service keeps raising English messages; its text is matched to
  the `error.*` entry with the same English text (`{name}` matches any value). A test scans
  `service.py` and `api.py` and fails when a raised message has no entry, naming the line.
- **A language:** add a `Locale(...)` to `LOCALES` in `i18n.py` and a `locales/<code>.json`.
  A language only needs the keys to be complete; missing ones fall back to English, but the
  test suite requires them all.

The translations were machine-drafted and should be reviewed by native speakers before
going in front of users.

## 5. The web pages (`static/i18n.js`)

The portal and builder load `static/i18n.js` (after `common.js`, before `auth.js`). It puts a
language picker (a globe and a list of languages, each in its own language) in the top
bar, and handles everything else:

- **Choosing:** the language saved in this browser, else the browser's language
  (`navigator.languages`), else English. Picking one switches the page at once, without a
  reload, sets `<html lang dir>` (Arabic is right to left) and sends it as
  `Accept-Language` on API requests, so errors come back in that language.
- **Remembering:** the choice is kept in `localStorage`, and, when someone is logged in,
  saved on their account with `PATCH /users/{id}`. On login, an account that has a saved
  language gets it (so it follows the person to another device); an account without one
  gets this browser's explicit choice.
- **Offline:** each catalog is also kept in `localStorage`, so the portal still shows the
  chosen language offline. It is refreshed in the background when the server's `version`
  changes.

Markup. English stays in the HTML, so a page works before (and without) its catalog; a
test checks that it matches `locales/en.json`.

```html
<button data-i18n="ui.action.save">Save</button>
<input data-i18n-placeholder="ui.action.search" placeholder="Search">
<!-- also: data-i18n-title, data-i18n-aria-label -->
```

Scripts that generate text call `I18n.t(key, {name: "x"}, "English fallback")` and redraw
on the `i18n-changed` event (`document.addEventListener("i18n-changed", ...)`). A script that
skips redraws when its data is unchanged should include `I18n.revision()` in what it
compares. A page that loads `auth.js` without `i18n.js` still works, in English.

To translate more of a page: add the keys to every `locales/*.json`, then add `data-i18n`
(or `I18n.t`) in the page. `tests/test_i18n.py` fails when a page uses a key the catalog
lacks, and `tests/web/i18n.test.cjs` covers the picker's logic. Remember to bump the
`?v=` of every script or stylesheet you change (in the HTML and in `portal-sw.js`, whose
`CACHE` name must change too), or browsers and installed apps keep the old version.

## Not covered yet

- On the web pages, the portal and builder shell, the login dialog and the game cards are
  translated (see below). Still English: the token wallet and stake panel, the install
  and notification help, offline-sync messages, most messages the portal and builder
  generate while running, `/admin`, `/stats`, `/browse` and `/console`. Texts that come
  from data (game names and descriptions, account names) are shown as written.
- Games' own text (name, description, in-game UI) is written by the game's builder: it is
  translated on demand by Google Translate, from a string table the game declares; see
  `docs/game-translation.md`.
- Pydantic's 422 validation messages stay English.
